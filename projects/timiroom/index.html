화면

개요

기획서와 API 명세, DB 설계가 따로 만들어지면 기획이 바뀔 때마다 세 문서를 대조하며 고쳐야 하고, 어긋남은 개발을 시작한 뒤에야 드러납니다. Align-it은 이 문제를 줄이려고 만든 서비스입니다. 채팅으로 아이디어를 말하면 PRD, 기능 명세, API 명세, DB 스키마, QA 시나리오를 만들고, 그 산출물끼리 그리고 실제 코드와 맞는지 다시 검증합니다.

6명이 팀 TIMIROOM으로 함께 만들고 있고, 2026 한이음 드림업 과제로 진행합니다. 핵심 추론은 LG AI연구원의 K-EXAONE과 업스테이지의 Solar 같은 국내 모델로만 구성했습니다.

동작 흐름

  1. 채팅으로 요구사항을 말하고 참고 PDF를 올립니다.
  2. 한국어 Hybrid RAG가 기존 문서와 산출물에서 근거를 찾습니다.
  3. Search·PM·PRD·DBA·API·QA 여섯 에이전트가 각자 하나의 역할만 맡아 설계 산출물을 차례로 만듭니다.
  4. QA 에이전트가 PRD·DB·API 사이의 모순과 누락을 검수하고, 문제가 있는 항목만 최대 3회까지 다시 생성합니다.
  5. GitHub 저장소를 연결하면 Pull Request의 변경 코드를 확정된 설계와 비교해 리뷰 코멘트를 남기고, 후속 작업은 Issue로 만듭니다.
flowchart TD
  U[요구사항 · 참고 PDF] --> R[한국어 Hybrid RAG]
  R --> A[여섯 에이전트 설계 생성]
  A --> Q[QA 교차 검수]
  Q --> D[PRD · API · DB · QA 산출물]
  D --> G[GitHub PR 정합성 리뷰 · Issue]

맡은 일

백엔드, 프론트엔드, 운영 저장소를 오가며 작업했고, 지금까지 백엔드 12개, 프론트엔드 6개, 운영 9개의 Pull Request를 올렸습니다.

  • Java 21, Spring Boot 기반 백엔드와 멀티 에이전트 파이프라인 연동
  • Spring Security, OAuth2, Redis Session으로 로그인과 세션 구성
  • WebFlux와 SSE로 AI 문서 생성 단계를 화면에 실시간으로 전달
  • Spring Data JPA로 PostgreSQL을 연동하고 Neo4j, Kafka 연결
  • GitHub App 연동과 Pull Request 정합성 리뷰 기능
  • 서비스를 NAS의 K3s에 올리고 배포 파이프라인 구성

한국어 Hybrid RAG

한국어 기획 문서는 고유명사와 복합명사가 많아서 벡터 검색만 쓰면 로그인, 결제 같은 도메인 용어가 엉뚱한 문서에 매칭되곤 했습니다. 의미가 비슷한 문서와 용어가 정확히 일치하는 문서를 함께 찾도록 검색을 두 갈래로 나눴습니다.

단계 처리
질의 구성 프로젝트, 문제, 사용자, 핵심 기능 등 5개 관점으로 질의 확장
병렬 검색 Solar Embedding 2 벡터 검색(pgvector)과 PostgreSQL 키워드 검색을 동시에 실행
순위 결합 두 순위를 RRF로 합산
재순위화 Solar Pro 2가 후보를 비교해 최종 5건과 선택 이유를 반환

검증 결과

평가 결과
한국어 검색 (질의 12건, 후보 22건) Top-1·Top-3 정확도 100%, MRR 1.000
리랭킹 (질의 3종, 후보 12건) Solar Pro 2가 Precision@3 1.00, 응답 1.19초로 비교 모델 중 가장 빠름
설계 생성 End-to-End 서로 다른 두 서비스 모두 구조 검증 통과, PRD 필수 섹션 9/9
자동 테스트 설계 생성 52건, 정합성 검증 30건, 82건 전수 통과

LLM이 만든 판정은 그대로 믿지 않습니다. 코드는 Tree-sitter, Python AST, SQLGlot 같은 결정적 파서가 먼저 읽어 사실을 뽑고, K-EXAONE은 그 사실과 설계 문서가 같은 뜻인지만 판단합니다. 근거를 원문에서 다시 확인하지 못한 결과는 버리고, 판단 자료가 부족하면 억지로 결론 내지 않고 INCONCLUSIVE로 남깁니다.

지식 그래프 영향도 분석

기능, API, 테이블은 서로를 가리키는 식별자가 없어서 명세 텍스트만으로 관계를 찾아야 합니다. 기능 이름의 낱말이 API 설명에 나타나는지, API 경로의 리소스 이름이 테이블 이름과 같은지를 기준으로 관계를 복원하고, 그래프에서 항목 하나를 고르면 바로 닿는 항목과 한 다리 건넌 항목을 단계별로 강조합니다. 어디에도 이어지지 않는 항목은 점선으로 따로 모아 설계가 빠졌는지 보게 했습니다.

실제로 생성한 냉장고 관리 서비스 명세(기능 12개, API 13개, 테이블 8개)에서 users 테이블을 고르자 확인 대상이 15개로 좁혀졌고, 코드 변경을 올리자 응답 형태가 명세와 다른 API 하나를 병합 전에 찾아냈습니다. 이 내용은 한국정보처리학회 학술대회(ACK 2026) 논문으로 정리했습니다.

배포

코드를 올리면 GitHub Actions가 이미지를 만들고, 운영 저장소의 manifest가 바뀌면 Argo CD가 K3s에 반영합니다. 새 버전은 Argo Rollouts의 Blue-Green 방식으로 교체하고, 외부 요청은 Nginx가 HTTPS로 받아 전달합니다.

flowchart TD
  P[GitHub push] --> A[GitHub Actions 이미지 빌드]
  A --> M[운영 저장소 manifest 갱신]
  M --> C[Argo CD 동기화]
  C --> R[Argo Rollouts Blue-Green]
  R --> K[NAS K3s]
  K --> N[Nginx HTTPS]

현재 단계와 다음 작업

검색, 설계 생성, 정합성 검증, GitHub 리뷰까지 하나의 흐름으로 동작하고, 11월 초 1차 결선 시연을 준비하고 있습니다. 다음 단계는 산출물의 기능, API, 테이블, 테스트, 코드를 노드로 잇는 지식 그래프로 변경 영향 범위를 자동으로 추적하고, 팀원이 승인한 수정만 반영하는 흐름을 완성하는 것입니다. 지식 그래프를 적용하기 전과 후의 영향 범위 탐지 정확도(Precision·Recall·F1)와 검토 시간도 비교할 계획입니다.
